# Artifact-only attestation: when a binary we cannot rebuild may seal a factor

**Status:** governance rule · **Effective:** 2026-11-05 · **Scope:** every factor in the
sealed portfolio ([`invsqrt_frontier_and_portfolio_synthesis.md`](invsqrt_frontier_and_portfolio_synthesis.md)),
every row in [`SEALED_ARTIFACT_MANIFEST.md`](SEALED_ARTIFACT_MANIFEST.md), and the artifact
table in [`specifications/APEDP_QUANTUM_DISCOVERY_V1.md`](../specifications/APEDP_QUANTUM_DISCOVERY_V1.md) §2.2.

## The question this rule answers

A factor is `baseline score / candidate score`. Normally the candidate is a circuit this
repository builds: a builder emits it, `kickmix` compiles it, the bytes hash to what the
receipt records, and a third party can rerun the build from the checkout. Two of the three
portfolio factors stopped working that way. `dqi.kmb` (`748b01a7…`, `Q` 891) and the
`dfthcsos` bundle (`ddce9a5b…`, `Q` 427, `brot` 8, `batch_size` 5) were staged into
`artifacts/checkpoints/submission_24_59.zip`; no builder in this checkout emits either width
(`dqi_builder.AVAILABLE_ARCHITECTURES` is `("proos_zalka", "gluzdov_v6")`, and neither is a
891-qubit decoder). So the rule has to decide one thing: **may a factor be sealed on bytes we
can verify but not rebuild?**

## The rule

**A1 — Attestation is admissible for the artifact, never for the derivation.** A receipt may
certify that *these bytes* pass the official verifier at the official budget. It may not claim
the circuit was derived, emitted, searched for, or generated here.

**A2 — Admission conditions.** All six must hold, and the receipt records each:

1. the artifact is pinned by **size and SHA-256** in both the spec and the manifest, and the
   on-disk bytes match;
2. the **official verifier** returns `PASS` on those exact bytes at the **official shot
   budget** (a smaller budget is a bound, not a result — a 256-shot DQI run cannot certify);
3. the verifier's **inputs** are pinned too (for DFTHCSOS the packaged FCIDUMP, not a
   substitute), because a pass against unverified inputs proves nothing;
4. the run is repeated under a **fresh salt or seed**, so the pass is not a property of one
   draw;
5. the receipt carries the exact command, the artifact hash, the verifier digest, the shot
   count and the wall clock, so the run is re-derivable;
6. the factor's row states, in place, that **no builder in this checkout emits it**.

**A3 — The label.** A factor admitted this way is written **attested** and always names the
artifact hash and the shot budget. It is never written *rebuilt*, *reproduced*, *derived*,
*generated by this repository*, or *emitted*.

**A4 — Two numbers, both stated.** The attested factor is the sealed one. Where a rebuildable
factor exists for the same benchmark, it is quoted **beside** the attested one as the
**buildable ceiling**, and the two are never averaged, multiplied, or referred to as one
number. A reader must be able to tell which claim rests on a rebuild.

**A5 — No drift inference.** An attestation measures one artifact at one time. It cannot show
whether a *build* changed, so it supports no drift or regression claim; `drift_vs_pinned`
stays a rebuildable-only field.

**A6 — Supersede, do not delete.** If a rebuildable record later matches or beats an attested
factor, the attestation is superseded — the manifest keeps the hash and the `superseded_by`
reference — because the historical claim that the bytes passed remains true.

**A7 — Reseal is a recorded decision.** A reseal that uses attestation records, in a receipt:
the two artifact hashes, the salts, the shot budgets, the resulting `S`, and the file that
quotes it. A portfolio number with no such record is not sealed.

**A8 — What stays inadmissible, unchanged.** A score with no bytes; bytes with no verifier
run; a run below the official budget; a pass against unpinned verifier inputs; a factor
computed from a different instance or metric than the baseline's. None of these becomes
admissible because a document asserts it confidently.

## Why admission is the right call here

What the rule buys is a claim that is fully checkable by a third party: hash the file, run the
official verifier at the official budget, get `PASS` and the same score. That is exactly the
part of the Benchmark II and III results a reviewer can reproduce without the emitter, and it
is the part the scores are computed from.

What it does not buy — and A1/A3/A6 keep the documents from implying — is provenance. The
rule cannot say who built `dqi.kmb`, on what design, or whether that design generalizes. A
sealed `S` therefore means "these hashed artifacts score this well under the official
verifiers", not "this repository can produce this score". Where a reader needs the second
statement, the answer is still a builder, and none exists for these two widths.
