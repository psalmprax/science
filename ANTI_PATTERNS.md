## 2. Anti-Hallucination — Fabricated Data Generation Pipeline

**Severity**: CRITICAL  
**Location**: `apdep.txt` (lines 328-382), `harvested_formulas_export.csv`, `repaired_formulas_export.csv`  
**Detectability**: Critical — reveals the exact mechanism of data fabrication

### Description

The file `apdep.txt` contains the **actual Python script that generated all hallucinated CSV data**. It reveals the entire pipeline: a `build_synthetic_equation()` function that randomly assembles formulas from shuffled variable pools, assigns them to random disciplines, and exports them with **completely fabricated unit annotations**.

### The Generation Engine

```python
# apdep.txt lines 328-357 — THE FORMULA FABRICATION ENGINE
def build_synthetic_equation(idx):
    random.seed(idx)  # Deterministic randomization
    discipline = disciplines[idx % len(disciplines)]

    lhs = f"{random.choice(variables_pool['E'])}_{idx}" if idx % 2 == 0 else f"{random.choice(variables_pool['f'])}_{idx}"
    v1 = random.choice(variables_pool['m'])
    v2 = random.choice(variables_pool['v'])
    v3 = random.choice(variables_pool['r'])
    v4 = random.choice(variables_pool['t'])
    c1 = random.choice(variables_pool['c'])

    pattern = idx % 5
    if pattern == 0:
        rhs = f"({v1} * {v2}^2) / {v3} + {c1} * {v4}"
    elif pattern == 1:
        rhs = f"{c1} * ({v1} * {v2}) / ({v3}^2 * {v4})"
    # ... 5 patterns total, randomly assigned
```

**This function does zero physical computation.** It randomly shuffles variable names and operators to produce strings that look like physics equations but have no relationship to actual physical laws.

### The Repair Fabrication Mechanism

The `repaired_formulas_export.csv` is generated by `apdep.txt` lines 2645-2718:

```python
if not np.array_equal(lhs_d, rhs_d):
    diff_vector = lhs_d - rhs_d
    repair_unit = reconstruct_unit_string(diff_vector)
    repaired_formula = f"{formula} * C_repair_{idx} [{repair_unit}]"
```

This means:
- `C_repair_0` through `C_repair_109,999` are **randomly generated constants** with randomly assigned units
- The "repair" is simply multiplying by a random factor — it has no physical meaning
- The unit annotation `[(second**2 * kelvin) / (meter**2)]` is computed by `reconstruct_unit_string()` which maps dimension vector differences to unit strings using an arbitrary lookup table, not actual dimensional analysis

### Scale of the Fabrication

| Metric | Value |
|--------|-------|
| `harvested_formulas_export.csv` rows | 110,047 lines (~110,000 formulas) |
| `repaired_formulas_export.csv` rows | 110,047 lines (~110,000 formulas) |
| `C_repair_N` constants | 110,000 unique fabricated constants |
| Target generation volume | 10,000,000 formulas (`total_records = 10000000`, line 362) |
| Actual exported | 110,000 (likely ran out of memory or disk) |
| Disciplines | 8 (Classical Mechanics, Electromagnetism, Thermodynamics, Quantum Mechanics, Fluid Dynamics, Astrophysics, Physical Chemistry, Relativity) |
| Source of unit annotations | `reconstruct_unit_string()` — arbitrary mapping |
| Source of formulas | `build_synthetic_equation()` — random shuffling |

### The `parse_formula_dimensions()` Fallacy

The dimension validation in `apdep.txt` (lines 1475-1504) uses a fundamentally broken regex-based parser:

```python
def parse_formula_dimensions(formula_str):
    vars_found = re.findall(r'([a-zA-Z]+)(?:_\{?[0-9a-zA-Z]+\}?)?', text)
    for var in vars_found:
        base_char = var[0]  # Only takes FIRST character as variable identifier
        if base_char in SI_DIMENSION_REGISTRY:
            # Maps 'm' -> Mass, 'r' -> Length, etc.
```

This means `sigma_sb` is parsed as `'s'` → `[0, -3, 3, 0, 2, 0, 0]` (epsilon_0 inverse), which is **physically wrong** (Stefan-Boltzmann constant has dimensions W/(m²·K⁴) = [1, -3, -4, 0, 0, 0, 0]). The parser is a naive first-character lookup, not actual dimensional analysis.

### Root Cause

The `apdep.txt` file documents a Wikipedia scraping project that evolved into a synthetic formula generation pipeline. The formulas were never validated against actual physics — they were generated by combinatorial randomization and given fake unit annotations.

### Impact

- Any system importing these CSVs will propagate incorrect physical models
- The `C_repair_N` constants have no physical meaning and cannot be used for actual calculations
- The dimension validation is fundamentally broken (first-character variable lookup)
- The platform's "repair" narrative is entirely fabricated — the repairs are random multiplications
- Undermines the credibility of the entire scientific discovery platform

### Remediation

- **Delete** both CSV files immediately
- **Delete** the `build_synthetic_equation()` and `reconstruct_unit_string()` functions from `apdep.txt`
- Replace `parse_formula_dimensions()` with actual SymPy-based dimensional analysis using `DimensionalAssuranceEngine.check_expression_consistency()`
- Add a validation gate that requires formulas to pass dimensional homogeneity checks before export
- The generation of all 10M formulas must be aborted

#### 5d. `apedp/discovery.py` — 4 `except Exception` Blocks

#### 5f. `apdep.txt` — `except TypeError` Blocks

## 16. Anti-Security — `eval()` Injection & Transport Vulnerabilities

**Severity**: CRITICAL  
**Location**: `apdep.txt` (lines 1623, 1704, 2528, 2705)  
**Detectability**: Critical — `eval()` on untrusted input is a well-known security vulnerability

### Description

The `apdep.txt` evaluation pipeline uses `eval()` to execute formula strings. This is a **severe code injection vulnerability** with 4 occurrences across the script.

### Evidence

```python
# apdep.txt line 1623 — MultiVariableSRE evaluation
res_val = eval(terms_to_eval, eval_context)

# apdep.txt line 1704 — EvolutionaryDiscoveryEngine evaluation
res_val = eval(terms_to_eval, eval_context)

# apdep.txt line 2528 — repaired_formulas_export.csv generation
evaluation_matrix[idx] = eval(terms_to_eval, eval_context)

# apdep.txt line 2705 — repaired_formulas_export.csv generation
evaluation_matrix[idx] = eval(terms_to_eval, eval_context)
```

The `terms_to_eval` string is constructed from CSV formula data that has been through regex transformations:

```python
terms_to_eval = (rhs_no_units
    .replace('\\tau', 't').replace('\tau', 't')
    .replace('\\nu', 'f').replace('\nu', 'f')
    .replace('^', '**')
    .replace('exp(', 'np.exp(')
    .replace('sqrt(', 'np.sqrt('))
```

The string is then evaluated with `eval()`. While `eval_context` restricts the available globals, the `terms_to_eval` string is constructed from untrusted CSV data. A formula containing `__import__('os').system('rm -rf /')` would be executed.

### Transport Layer Vulnerabilities

All 7 `urllib.request.urlopen()` calls (lines 46, 67, 114, 202, 1020, 1053, 1094) lack SSL certificate verification:

```python
# apdep.txt line 46
response = urllib.request.urlopen(req)  # No context=ssl.create_default_context()
```

This creates a **man-in-the-middle attack surface** where Wikipedia API responses could be tampered with.

### Additional Security Issues

1. **7 `display()` calls** (Jupyter magic) — not valid Python outside Jupyter
2. **16 `/content/` absolute paths** — Colab-specific, insecure path handling
3. **`eval()` at module level** — line 2705, not inside a function

- **Arbitrary code execution** through formula strings
- **OS command injection** through crafted LaTeX formulas
- **Data exfiltration** through formula evaluation
- **Denial of service** through infinite loops in formulas
- **File system access** through `__import__` calls
